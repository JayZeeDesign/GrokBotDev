# BUILD NOTES — F16 · hero bot family v2

M8 · branch `f16-hero-bots`. Separate from `BUILD-NOTES.md` on purpose: F16 was built in a
parallel clone while another executor held the main checkout, so its notes land in their own
file and get folded in at integration time.

**What F16 does.** Re-skins the home hero's physics bots so they read as real Grok Bot
interface avatars — soft silhouettes, flat solid fills, a fixed six-colour palette that does
not invert with the theme — and moves the old ink/paper/amber family to `/about/` as a
decorative static pile rather than deleting it. The physics simulation itself is unchanged.

**Harmonisation.** Raw lightness across the sampled avatars spanned 0.581–0.811 (spread
0.230). Shipped spread is 0.665–0.720 (0.055) — compressed but deliberately *not* flattened:
the warm hues keep a small lightness lead, because forcing orange down to a cool hue's
lightness turns it to mud. All six sit inside sRGB; worst pairwise oklab separation is 0.114
(blue vs purple), so no two read as the same bot.

**Contrast.** White facial features clear the 3:1 non-text floor on all six. Grey is the
tight one at **3.05:1** — that is the readability case the directive called out, and it is
why grey landed at L 0.665 rather than the eyedropped 0.670-and-lighter.

**Where they live.** `src/styles/hero-bots.css`, as `--bot-fill` on `.s2-<colour>`.

> **§4.1.1 exception, flagged deliberately.** That file's comment says `tokens.css` is the
> only file allowed to contain hex values. F16 breaks that on purpose and it needs an
> operator eye: these six **must not be tokens**, because a token inverts with the theme and
> real avatars do not. Putting them in `tokens.css` would also have meant editing a file
> outside F16's boundary. `check-contrast.mjs` only reads `tokens.css`, so no gate is
> weakened — but the convention now has one documented exception and that should be recorded
> in the main notes at integration.

**A1 side effect, in our favour.** v1 promoted exactly one bot to Ash Amber. v2 carries no
amber at all, so the hero stops spending the "one accent element per viewport" budget and
leaves amber entirely to the CTA and the search cursor. That is a tightening of A1, not a
bend.

### 2.1 · THE FORBIDDEN PAIRS — read this before adding any bot to family v2

This is the **durable constraint**, not just a record of what F16 did. Family v2 is a system
that will get new forms; every one of them has to clear this table, or the "cousin, not copy"
guarantee quietly stops being true the day someone adds a thirteenth bot.

**A form may not combine any of these nine silhouette + colour pairs:**

| # | silhouette | colour | which real avatar it would clone |
|---|---|---|---|
| 1 | circle | grey | shot A, avatar 1 |
| 2 | circle | orange | shot A avatar 3 · shot B avatar 6 |
| 3 | circle | teal | shot B, avatar 5 |
| 4 | circle | blue | shot B, avatar 9 |
| 5 | circle | red | shot B, avatar 10 |
| 6 | rounded triangle | orange | shot A, avatar 2 |
| 7 | rounded triangle | purple | shot B, avatar 7 (indigo) |
| 8 | horizontal pill | teal | shot A, avatar 4 |
| 9 | rounded square | purple | shot B, avatar 8 |

Read the other way round, this is what is still **available**:

| silhouette | colours left open |
|---|---|
| circle | **purple only** — this is why the family's one circle is purple |
| rounded triangle | blue · teal · red · grey |
| horizontal pill | blue · orange · purple · red · grey |
| rounded square / squircle | blue · orange · teal · red · grey |
| rounded rectangle (`r` < short-axis/2) | all six — no reference avatar is one |
| vertical capsule | all six — no reference avatar is one |
| ellipse (aspect ≥ 1.3) | all six — no reference avatar is one |

**Procedure for adding a form (v3, or any later addition):**

1. Check the new form's silhouette + colour against the nine pairs above. If it hits one, pick
   a different colour — a footnote does not clear it.
2. Add it to `FORMS_V2` in `src/scripts/botFamilyV2.js`.
3. Re-run `node scripts/qa/f16-deniability-grid.mjs <cropDir> <out.html>`. It **mechanically
   re-derives** the verdict from its own `REFERENCES` array, so it will catch a clash even if
   this table was not consulted. It prints `N/N pass` and marks any failing bot in red.
4. If the silhouette is a genuinely new class, extend `silhouette()` in that script too —
   an unclassified shape silently falls through to `squircle` and could mask a clash.
5. Keep every colour on at least two forms. With twelve forms and six colours, a roll dropping
   a whole colour sits at ~1.5%; with a singleton colour it jumps to ~9%.

The machine-readable copy of this table is the `REFERENCES` array in
`scripts/qa/f16-deniability-grid.mjs`. **These two must be kept in step** — if new reference
avatars are ever catalogued, update both.

**The decision this forced: colour is baked into the FORM, not rolled per bot.** A circle is
spoken for in five of our six colours. Had colour been rolled the way v1 rolled its amber
pick, some seeds would have produced a grey circle or a teal pill — an exact shape+colour
clone — and only the sampled seeds could ever have been checked. Baking it moves the
guarantee from *probably* to *always*: the twelve forms avoid all nine reference pairs by
construction, so **every seed is deniable, not just the rendered ones.** Purple is the one
colour the references never draw as a circle, so the family's single circle is purple. Ovals
sit at aspect ≥ 1.3 so they read as ovals rather than soft circles.

Variety per load is unchanged and still comes from the mechanics that always produced it:
ten of twelve forms drawn (v1: ten of eleven — the roster now rotates harder), per-bot size
mutation, per-bot eye-tilt mutation, drop position, and the visible seed.

**The eye axis was deliberately not used as the argument.** Every v2 bot wears our eye system
— two large PARALLEL slash capsules that blink and track the cursor. Every reference avatar
wears a smaller MIRRORED converging pair that never moves. That difference alone would have
cleared all twelve on a technicality, which is exactly the footnote the directive rules out,
so the grid's verdict is computed on **shape + colour alone** and the eye difference is
recorded as reinforcement.

## 3 · Geometry vs integration-notes §8

Every v2 form reports its collider through `bodySpecV2()`, so the drawn shape and the physics
body cannot drift apart. In all four branches **the collider bounds the paint**, which is the
property INFLATE 1.10 exists to guarantee.

| form class | paint | collider | §8 note |
|---|---|---|---|
| rounded rect / squircle / pill / capsule | `<rect rx=r>` | `Bodies.rectangle` chamfered at the same `r` | unchanged from v1 |
| circle | `<circle r>` | `Bodies.circle(r)` | exact — no approximation, nothing to retune |
| ellipse | `<ellipse>` | inscribed 18-gon | worst inward deviation 1.52%, two orders inside the INFLATE margin |
| rounded triangle | inset polygon + 16-unit round-joined stroke | the **full sharp** triangle | paint is at or inside the collider everywhere, strictly inside at the corners — same relationship v1 shipped |

**Triangle inset is now derived, not a magic number.** §8 warns that retuning a triangle's
`geo` without retuning `inset` makes it overlap its neighbours, and v2 has three triangles at
different proportions. `triInset()` computes `k = 1 − (strokeWidth/2) / dmin` on the tightest
centroid-to-edge distance, so no edge can paint outside the nominal silhouette.
**Validation:** for v1's 96×78 triangle the formula returns 0.692 — which is the 0.70 that
was hand-tuned by eye. It reproduces the tuning, so it is safe on the new proportions
(`rtriWide` 108×72 → 0.667, `rtriSmall` 84×72 → 0.667).

One difference from v1, deliberate: v1 applied a second `−centroid` translate on the group
*after* the polygon points were already centroid-relative, leaving its triangle and arch
drawn ~13 units above their colliders (absorbed by INFLATE). v2 draws every form
centroid-at-origin with an identity group transform, so paint and collider share one frame
exactly. **v1's own rendering is untouched** — §8 says leave it alone, and `botFamilyV1.ts`
reproduces the quirk byte-for-byte.

### No fusing — measured, 12 / 12 seeds clean

Family v2 is flat solid fill, so "fusing" has a precise meaning: two bots **of the same
colour** whose silhouettes merge into one shape. Different-colour bots resting against each
other are not a fuse — both are still readable.

`scripts/qa/f16-fusecheck.py` tests exactly that, on pixels: for each palette colour it
counts connected components in the rendered hero and compares against how many bots of that
colour the live DOM says are in the roll. Fewer components than bots = a fuse. Antialiased
boundary pixels are excluded by a tight colour tolerance, so a blend zone cannot bridge two
components.

**12 seeds, 12 clean, zero fuses.** Colour counts matched the DOM on every seed.

### The one physics change: released bots were never waking up

**This is a pre-existing bug F16 inherited, not one it introduced — measured at an identical
4-in-8 rate on the pre-F16 build.** It is fixed here in **its own commit** so it can be
reverted independently of the re-skin.

A bot waits off-stage as a *static* body until its stagger delay fires. With
`enableSleeping: true`, matter's `Sleeping.update` does **not** skip static bodies — it sees
zero motion and, after `sleepThreshold` (60 frames ≈ 1s), flags the parked bot asleep.
`Body.setStatic(body, false)` restores mass and restitution but deliberately does not clear
`isSleeping`, and `Engine._bodiesUpdate` skips sleeping bodies outright. So the bot is
released, repositioned and given a velocity that is never integrated: it hangs above the
stage forever, clipped by `overflow: hidden`, and **the hero renders nine bots.**

It bites the last bots in the stagger, whose delay `i*rr(70,150)+rr(0,120)` crosses the ~1s
threshold (i ≥ 8) — hence intermittent.

The fix is one line in `releaseDue()` — `Matter.Sleeping.set(b.body, false)` — which is the
same idiom integration-notes §7 already documents for the idle nudges ("Idle nudges explicitly
wake bodies via `Sleeping.set(body, false)`") and that `idleBehaviours()` already uses. It
**restores** the 10-desktop / 6-mobile count A4 and integration-notes lock rather than
changing it. Measured after: **0 stranded across 12 seeds** (from 4 in 8).

It only became worth fixing at F16 because v2's bots are large and brightly coloured, so a
missing one reads; against ten small black shapes it was invisible.

## 5 · The old family: bot family v1 on /about/

The ink/paper/amber cluster is not deleted. `src/lib/botFamilyV1.ts` carries all eleven forms
with their geometry, stroke insets and eye markup lifted unchanged — including the §8 quirks.

It renders on `/about/` under the "who keeps it current" story as a decorative static pile:

- **No second physics island.** No matter.js, no client script, no rAF loop on `/about/`.
  The pile is generated at build time into one inline `<svg>`; the page ships the exact same
  four `<script>` lines it shipped before F16. Verified by diffing the built HTML.
- **It reuses `renderStatic()`'s layout**, not a new drawing — the same `pileRows` 6/3/1
  taper, the same `rowH = avg * 0.78`, the same per-row `ri * 0.11` inset and the same
  deterministic `((k*37)%7 − 3) * 0.045` tilt.
- **No caption.** A7 binds every public string on that page. The safest way to honour it on
  a decorative illustration is to ship no copy at all, so the pile is `aria-hidden` and
  unlabelled; the prose beside it already uses the sanctioned names (the Scouts, the Curator,
  the Builder) and "always on".
- **`accent: false`, deliberately.** v1's rule was one Ash Amber bot. A1 caps amber at one
  element per viewport and `/about/` already spends its accent elsewhere, so the rule is
  switched off by an explicit flag rather than left to whichever form the seed lands on. The
  accent index is still drawn from the seed stream so toggling the flag cannot reshuffle the
  pile.

**One retuning note.** The hero derives bot *size* from the **stage** width but cluster width
from the narrower measured `#content` block (~1440 vs ~880 at desktop). Collapsing those into
one number made the pile sparse — 67px bots scattered across a 653px cluster instead of
piling. `renderStaticPileV1()` therefore takes `width` (the cluster) and `stageWidth` (the
bot scale) separately, which reproduces the hero's real cluster-to-bot ratio of about 7.3 : 1.

## 7 · The circle rule

> **Circles are allowed in the hero illustration family only.**

Addendum A3's trademark rule — *no circle silhouettes as marks: solid, hollow, or dotted* —
is **unchanged and remains absolute** for the logo, the favicon, OG cards, chips and every
other mark surface. The single circular form in family v2 (`dot`, purple) is decorative
illustration inside an `aria-hidden` bot layer, and that is the only place a circle is
permitted.

This line is carried in three places so it cannot be lost: the C3 block in
`src/styles/hero-bots.css`, the callout at the top of the `/dev/components` bot-family
section, and here.
